## Item 1: `src/mailbox/maildir.cs` — missing/inaccessible directories silently swallowed into an empty enumeration

Rust's `FolderIterator::new()` does `fs::read_dir(path)?` — a missing or inaccessible root is a hard error at construction, not an empty result; read failures mid-traversal are likewise propagated as `Err`, never silently skipped. The rewrite from the prior round had `if (!Directory.Exists(_rootPath)) yield break;` in `GetEnumerator()` and `catch (IOException) { yield break; }` / `catch (UnauthorizedAccessException) { yield break; }` around the read in `Walk()` — both made an inaccessible mailbox indistinguishable from "just empty."

Fixed by removing both defensive catches entirely, letting `Directory.EnumerateFileSystemEntries` throw its natural .NET exception. Verified on disk after the fix:
```
    public IEnumerator<MaildirFolder> GetEnumerator()
    {
        if (Directory.Exists(_rootPath) && HasCurAndNew(_rootPath))
        {
            yield return new MaildirFolder(_rootPath, null);
        }

        foreach (var folder in Walk(_rootPath, new List<string>()))
        {
            yield return folder;
        }
    }

    private IEnumerable<MaildirFolder> Walk(string dirPath, List<string> nameStack)
    {
        var entries = Directory.EnumerateFileSystemEntries(dirPath);
```
No `yield break` on missing root, no `try`/`catch` around the read. Regression test `missing_root_throws_instead_of_silently_empty_matches_rust`: points the iterator at a nonexistent path, asserts `DirectoryNotFoundException` via `Assert.ThrowsExactly`. Passing.

## Item 2: `src/mailbox/maildir.cs` line ~129 — Unicode-aware flag-suffix parsing instead of ASCII-only

Rust iterates the `cur`/`new` filename's `:2,FLAGS` suffix as raw bytes and checks `ch.is_ascii_alphanumeric()` — ASCII only (`0-9`, `A-Z`, `a-z`), stopping at the first byte outside that range. The rewrite used `char.IsLetterOrDigit(ch)`, which is Unicode-aware. Boss traced the exact failure by hand: for suffix `"2,XéF"`, Rust stops at the non-ASCII `é` and never reaches `F` (`Flagged` not set); C#'s `IsLetterOrDigit('é')` returns `true`, so parsing continued past it and incorrectly picked up `Flagged` from the trailing `F`.

Fixed with a direct ASCII-range check, matching this codebase's established pattern (`HeaderExtensions.IsAsciiWhitespace`/`EqIgnoreAsciiCase`). Verified on disk after the fix:
```
                        default:
                            if (!((ch >= '0' && ch <= '9') || (ch >= 'A' && ch <= 'Z') || (ch >= 'a' && ch <= 'z'))) goto flagDone;
                            break;
```
Regression test `flag_parsing_stops_at_first_non_ascii_alphanumeric_byte_matches_rust`: a real maildir message file named with suffix `2,XéF`, asserts the parsed flags do **not** include `Flagged` (matching Rust stopping at `é`, where the unfixed code would have incorrectly included it). Passing.


### `lib.rs` ↔ `lib.cs` — the remaining ~35-40%, now fully read — the "mostly JSON infra" characterization was WRONG, and a real bug was hiding in the unread part

Boss's instruction was explicit: don't assume the earlier "mostly JSON-serialization infra" note was correct -- read what's left and confirm, or find what's actually there. **Found and FIXED: `HeaderNameUtils.ParseHeaderName` (the C# equivalent of Rust's `impl From<&str> for HeaderName`) had no character validation at all.** Traced the actual Rust mechanism (`HeaderName::parse` in `parsers/header.rs`, previously only read for its whitespace bug, not its full body): it validates STRICTLY, character by character -- `[A-Za-z0-9_-]` only, ASCII-lowering uppercase as it goes -- and returns `None` the instant it hits anything else, INCLUDING plain whitespace. `From<&str>` then does `.unwrap_or(HeaderName::Other("".into()))`, discarding the entire original string on any invalid character, not just the bad part. C#'s version just looked the raw string up case-insensitively and fell back to `Other(originalString)` unconditionally -- never rejecting anything, never discarding to empty.

**Self-caught regression during the fix, instructive:** Rust actually has two related-but-different functions here -- `HeaderName::parse()` returns `Option<HeaderName>` (used directly by the stream tokenizer in `parsers/header.cs`, which applies its OWN fallback: `HeaderName.parse(rawStr) ?? HeaderName.Other(rawStr)`, correctly preserving original text on failure), while `From<&str>` calls `parse()` and unwraps it with ITS OWN different fallback (discarding to empty). The first fix conflated these into one function, which caused `ParseHeaderName` to return `Other("")` instead of a real failure signal -- silently defeating the tokenizer's `??` fallback and breaking 2 tests, including `parse_full_messages` (the 107-EML corpus). Caught immediately by the mandatory full-suite run after the change, not shipped. Fixed by splitting into an internal `ParseHeaderNameStrict` (returns `HeaderName?`, matches `HeaderName::parse` exactly) that both `HeaderName.parse(string?)`/`HeaderName.parse(ReadOnlySpan<byte>)` AND the public `ParseHeaderName` (which now applies `?? HeaderName.Other("")` itself, matching `From<&str>` exactly) call into. 4 regression tests added covering both the fixed implicit-conversion path and a guard against re-introducing this exact conflation. ## BEHAVIOR PARITY

This is where most of this audit's findings live — organized by theme, each with a file reference back to the full writeup:

**Silent-wrong-result bugs (most severe — no crash, no error, just a different answer than Rust for the same input):**
- `HeaderValue.as_text()`/`as_text_list()` and every hand-rolled caller that unpacks a `TextList` manually take the **first** element where Rust takes the **last** — confirmed independently in `lib.cs`, `message.cs` (`message_id`, `content_id`, `return_address`), and originally flagged by the earlier code-review at `lib.cs:516` (FILE 2, Coordinator Leads #1-2)
- `return_address()` falls back to checking Return-Path-as-Address instead of the **From** header when Return-Path isn't text-shaped — the documented "falls back to From" behavior is dead code in C# (FILE 2, Lead #12)
- Standalone `quoted_printable_decode()` cannot signal failure at all (wrong return type) and fabricates recovery bytes in 3 separate places instead of aborting like Rust — the single worst function found (FILE 10). Its sibling functions in the same file, `decode_quoted_printable_mime`/`_word`, are fully exact — the bug is isolated, not systemic
- `ContentType.attribute()` / `MessagePart.is_content_type()` / `Address.contains()` / `is_multipart_end()`: case-**insensitive** in C# (`OrdinalIgnoreCase`) where Rust is exact/ASCII-only — recurs in at least 5 places (FILE 2 Lead #5, FILE 3, FILE 16, cross-check #1/#2)
- `parsers/header.cs` and `quoted_printable.cs` use Unicode `char.IsWhiteSpace` where Rust uses ASCII-only `is_ascii_whitespace()` — 0x0B (vertical tab) is the cleanest concrete counterexample: whitespace in .NET, not in Rust (cross-check #1/#2, confirmed at the exact claimed lines)
- `Message.remove_header()` uses order-preserving `RemoveAt` where Rust uses order-breaking `swap_remove` (FILE 2)
- `header_raw()`/`headers_raw()` use lossy `UTF8.GetString` where Rust's `.ok()` on invalid UTF-8 returns `None` (drops the header) — C# never drops, always substitutes replacement chars (FILE 2)
- `Message.raw_message()` returns the **entire** backing buffer unsliced where Rust slices to the root part's bounds (FILE 2); the same unsliced-vs-sliced question was resolved as **correct, not a bug** for `PartType.len()` after finding its true Rust counterpart in `core/body.rs` (FILE 5 self-correction) — a reminder that this audit corrects itself when it finds it compared against the wrong symbol
- `HeaderForm.URLs` silently routes to `parse_raw()` instead of `parse_address()` (FILE 2)
- `resent_cc()`: pinned Rust reads the wrong header (`ResentTo` instead of `ResentCc` — a real upstream bug in the exact pinned commit) and C# silently "fixed" it with no record of the decision (FILE 2) — **flagged for Boss, not resolved**
- `MessagePart.is_text()`/`is_binary()` are narrower than Rust's (exclude Html/InlineBinary respectively) (FILE 2)
- `decode_hex()` adds a post-loop check that flips a truncated-but-recoverable escape from success to failure — traced all the way through to a concrete RFC 2231 filename-corruption scenario in `content_type.cs` (FILE 9, FILE 15)
- `DateTime.to_rfc822()`: missing the zero-offset sign guard (`-0000` vs `+0000`) and fabricates `"Jan"` instead of an empty string for an out-of-range month (FILE 4, both newly found, not in the original code-review)
- `obs_zone()` (obsolete timezone abbreviations) is case-insensitive in C# where Rust's `hashify::tiny_map!` is exact-byte (cross-check #4, upgraded from PLAUSIBLE to CONFIRMED)
- `mailbox/maildir.cs`: requires only ONE of `cur`/`new` to exist (Rust requires both); always uses `.` as the folder-name separator regardless of the configured prefix (Rust uses the prefix, or `/` for the documented `LAYOUT=fs`/no-prefix mode); and the whole folder-discovery **algorithm** is architecturally different — a recursive OS directory walk vs. Rust's flat single-level scan matching Maildir++'s real on-disk convention (FILE 13)

- `parsers/fields/content_type.cs` fabricates a real `ContentType` result at true EOF-with-no-trailing-newline where Rust discards everything and returns `Empty` — traced to an entire extra finalization block with no Rust counterpart (FILE 15)
- `parsers/fields/address.cs`'s `parse_address_detail_part` locks onto the **first** `+` and rejects an empty detail, where Rust tracks the **last** `+` and allows one — both example inputs from the cross-check traced exactly (cross-check #5)
- `parsers/mod.cs`'s `bytes_span()` **clamps** an out-of-bounds end position instead of rejecting the whole request like Rust's `.get(range)` does — high-blast-radius given how many field parsers call this primitive, though not traced to a specific reachable caller failure (FILE 19)
- `parsers/message.cs`'s inline/attachment heuristic has inverted polarity for a MIME part with **no `Content-Type` header at all** — a real, common case (RFC 2045 default), not an exotic edge case (FILE 20)
- `thread.cs`'s Hebrew "forwarded" prefix string appears to have an extra character relative to Rust's — flagged with appropriate hedging since RTL Unicode text is hard to verify by eye alone (FILE 18)

## KNOWN INTENTIONAL DIFFERENCES

**Two decisions explicitly reserved for Boss, neither resolved unilaterally in this audit:**

**Legitimate idiom differences, explicitly NOT classified as bugs anywhere in this document:**
- Rust's move-semantics builder chaining (`mut self -> Self`) vs. C#'s mutate-and-return-`this` — identical observable chaining behavior (`core/builder.rs`)

- `mime.cs`'s unconditional `.ToArray()` materialization — confirmed performance/memory-only (defeats zero-copy, doesn't change byte content) (FILE 16)
- C#'s defensive `buf.Count > 0` guard before a boundary-truncation `RemoveRange` in `decode_quoted_printable_mime` — a robustness improvement over an edge Rust itself would panic on, not a divergence on any input Rust handles successfully (FILE 10)
- The `MultiByteCharsetUtils`/`decode_charset` architectural choice to use .NET's `CodePagesEncodingProvider` instead of a WHATWG-standard library (no .NET equivalent to `encoding_rs` exists) — architecturally sound, byte-exact equivalence on malformed input not verifiable without execution (FILE 7-8)

## FILE 13: mailbox/maildir.rs -> mailbox/maildir.cs — known findings confirmed, plus a deeper architectural divergence

Rust's `FolderIterator` walks the directory tree **one level at a time via an explicit stack** (`it_stack`/`name_stack`), matching Maildir++'s real on-disk convention: nested folders are stored as **flat, dot-prefixed sibling directories** at the root (e.g. `.Work`, `.Work.Projects` sitting directly under the maildir root, not OS-nested), not via actual filesystem nesting. C#'s `MaildirFolderIterator` instead uses `Directory.GetDirectories(root, "*", SearchOption.AllDirectories)` — a **recursive OS directory-tree walk** collecting every subdirectory at any depth, then deriving the folder name from the filesystem-relative path. These are two different algorithms modeling two different on-disk layouts, not just a parameter difference.

| Symbol | Classification | Detail |
|---|---|---|
| `cur`+`new` requirement | **SEMANTIC_MISMATCH — confirmed, exact locations** | Rust (`maildir.rs:81-97`, `MessageIterator::new_`): returns `Err(NotFound)` if `cur` is missing, **and separately** returns `Err(NotFound)` if `new` is missing — both required, checked independently, either one absent fails the whole folder. C# (`maildir.cs:172`): `if (Directory.Exists(cur) \|\| Directory.Exists(new))` — either one alone is sufficient to treat the directory as a valid mailbox folder. A directory with only `cur/` (no `new/`) — a half-initialized or corrupted maildir — is silently accepted as a folder in C#, rejected in Rust. |
| Folder-name join separator | **SEMANTIC_MISMATCH — confirmed, and broader than the original finding** | Rust (`maildir.rs:165`): `self.name_stack.join(self.prefix.unwrap_or("/"))` — uses the caller-supplied `prefix` as the separator when one is given, or `"/"` when `prefix` is `None`. **`prefix: None` is an explicitly documented, intended usage mode** — the doc comment on `FolderIterator::new` (`maildir.rs:49-50`) says "For Dovecot Maildir mailboxes using LAYOUT=fs, use `None` as the prefix," which would produce `/`-joined folder names in Rust. C# (`maildir.cs:179`) **always** replaces path separators with `.`, regardless of `_prefix` — including when `_prefix` is `null`. For the Maildir++ case specifically (`prefix = "."`), Rust's separator also happens to be `.`, so this specific test configuration doesn't visibly diverge — but the `LAYOUT=fs`/`None`-prefix mode, and any custom non-`.` prefix, would produce different folder names between the two ports. The earlier review's "Work/Projects vs Work.Projects" example is the `None`-prefix case exactly. |
| Overall folder-discovery algorithm | **NEW FINDING — architectural divergence, not yet reduced to a single concrete failing input** | As described above: flat single-level dot-name convention (Rust) vs. recursive filesystem-nesting walk (C#). For the simple flat test fixture used in both ports' own tests (`.Work`, `.Work.Nested Folder` as literal directory names at the root), the two algorithms happen to produce matching results, which is presumably why the existing test suites pass. They would very plausibly diverge for: a maildir with genuinely OS-nested subdirectories (C# would recurse into them and report folders Rust's flat single-level scan would never see); directories that don't start with the configured prefix at all (Rust's per-level `strip_prefix` rejects them outright at the point of discovery; C#'s single `rel.StartsWith(_prefix)` check on the full computed relative path is a materially different test); or a `prefix: null` configuration relying on real OS nesting (the `LAYOUT=fs` case) where C#'s recursive walk might actually be the more "natural" fit for that layout, ironically, while Rust's stack-based walker still expects flat-per-level structure even in the no-prefix mode. Flagging this as needing a dedicated differential test with a nested-and/or non-matching-prefix maildir fixture, since reasoning about it further by inspection alone risks guessing rather than verifying. |

Rust's `Message` struct fields (`internal_date`, `flags`, `contents`, `path`) and flag-character parsing (`P`/`R`/`S`/`T`/`D`/`F`, stopping at the first non-alphanumeric char after `"2,"`) map cleanly to C#'s `MaildirMessage` — verified equivalent, no divergence in the per-message flag-parsing logic itself.

This file defines the low-level byte-cursor (`MessageStream`) that every single parser file audited in this document is built on top of (`next()`, `offset()`, `bytes()`, `try_skip()`, etc.). Given how much depends on it, spot-checked the highest-leverage primitives rather than skipping it as boilerplate.

| Symbol | Classification | Detail |
|---|---|---|
| `bytes()` / C# `bytes_span()` | **SEMANTIC_MISMATCH — confirmed, high-impact given call frequency** | Rust (`mod.rs:102-104`): `self.data.get(range).unwrap_or_default()` — `slice::get(range)` returns `None` (→ empty slice) if **either** `start > end` **or** `end > data.len()`; an out-of-bounds end position makes the whole call return empty, full stop. C# (`mod.cs:133-139`): explicitly **clamps** `end` down to `_data.Length` if it exceeds it, then returns `data[start..end]` with the clamped end — a non-empty, partial slice — rather than empty.
